# OPT-03：卡片预算与长内容交付

状态：分片 1、2 已实施（commit `a393376`），分片 3 的附件路径未实施（以 `/last full` 无损分页替代）。本地验证通过、现场未验证。优先级 P1。实施记录见文末。

## 问题与目标

当前正文窗口与思考窗口主要按字符串长度限制，工具摘要有界，但多块文本、JSON 转义、中文与控制组件仍可能使整体序列化体积增长。应对最终 payload 建预算，而非只分别限制正文字符数。

借鉴 [OpenClaw 的分段设计](https://docs.openclaw.ai/channels/feishu/advanced-configuration)：它明确将序列化开销纳入消息预算。具体 API 大小限制必须按本项目实际 create/update/send 路径分别验证；不能把其文档中的数值当作所有飞书接口的统一限制。

## 推荐行为

- 同时约束元素内容与整体 payload；以实际 UTF-8 序列化字节计量，预留控制和状态文案空间。
- 运行中优先保留当前状态、最新思考、最新正文、必要的停止控制。
- 完成后提供摘要及完整结果入口；大内容使用明确分页、分段或受权限保护的附件。
- 每次省略都说明访问完整内容的方式；不要引用仍然会二次截断的接口作为“完整”保证。
- 不能仅为了发得出去而删除失败信息、终态或结果链接。
- Markdown 边界断开需修复展示，原始记录不得因此被改写。

## 代码入口

`src/card/run-state.ts` 的 windowState/finalReplyText，`src/card/run-renderer.ts`，`src/card/tool-summary.ts`，`src/bot/channel.ts` 的最终答复和 fallback，OPT-01 的记录分页模块。

## 分片

1. 为实际投递路径建立可测试的 payload 大小检测与边界样例。
2. 运行卡片预算与降级；包含工具摘要、按钮、提示文字。
3. 最终长内容完整交付；保留分段身份和顺序，失败可重试且不重复已送达部分。

## 验收

- 超长中文、emoji、反斜杠/引号、代码、许多小文本块都落在所选接口预算内。
- 同一输入多次渲染的分段稳定；所有原始片段能按序重建，不能遗漏或重复。
- API 拒绝超限时有降级结果，不重复发送同一超限 payload。
- 短答复不被拆成多条；最终结果与过程预览不重复刷屏。
- 中途分段失败时知道哪些部分已送达，且错误提示不伪装为完整成功。

## 不做

不在本任务扩展所有媒体类型，不强制引入公网网站或外部存储服务。附件方案须使用既有安全路径并明确谁能访问。

## 实施记录（2026-09-17，基线 e4e45a3）

### 所选设计

- **预算计量**：`renderCardBounded`（`src/card/run-renderer.ts`）以 `Buffer.byteLength(JSON.stringify(card),'utf8')` 计量实际投递字节；`CARD_PAYLOAD_BUDGET_BYTES = 24_000` 为保守默认值，**不是飞书官方上限**，具体接口上限仍需按文档核验（可用 `budgetBytes` 覆盖）。
- **降级阶梯**：四级（思考窗口 1500→600→240→0；正文窗口 4000→2000→900→350），先收思考再收正文；逐级渲染并复测字节，首个达标即输出。终态通知、错误说明、终止按钮在每一级都渲染——降级不隐藏失败。输入状态不被修改；未触发降级时输出与原 `renderCard` 路径逐字节一致。
- **接入点**：卡片流式更新、降级进度卡、Codex 保留末答卡片全部改走预算渲染。doctor 卡未接入（低频、管理命令）。
- **最终长内容完整交付**：`/last full [页]` 对 `sessions.lastRunOutput`（onTerminal 已存的完整 run 正文）无损分页，每页 2,800 字符，页边界共享并避开代理对拆分；所有页拼接与存储内容完全相等，多次渲染稳定。数字参数保持旧行数语义，不破坏既有交互。默认 `/last` 视图与完成通知在超长时指向 `/last full`，不再把会二次截断的视图当作"完整"。
- **分片 3 的附件方案未实施**：分页已提供完整访问路径且无新增权限面；附件（文件上传）涉及新的访问与安全边界，按"不悄悄缩减、也不悄悄扩大"原则留待单独决策。
