# OPT-06：任务视图、完成凭据与自适应展示

状态：完成凭据分片已实施（commit `3e23c40`）；任务视图重设计与自适应信息密度未实施。优先级 P2。依赖的 OPT-01 记录入口已就绪。实施记录见文末。

## 产品目标

移动端默认卡片回答四个问题：正在做什么、最近完成什么、是否需要用户处理、结果在哪里。完整记录作为可展开或可查询的第二层。保留详细模式，不强迫用户只看摘要。

参考 [feishu-bridge](https://github.com/feir/feishu-bridge) 的 Todo/Agent 状态呈现，同时避免把模型、用量、版本、所有工具详情一起堆进主视图。

## 推荐信息层级

| 场景 | 主视图 | 次级视图 |
|---|---|---|
| 短任务 | 最终答复和结果入口 | 可选记录 |
| 长任务运行中 | 最近活动、阶段、耗时、投递状态 | 最新思考、工具汇总、历史 |
| 等待用户 | 待回答问题、可用操作、有效期 | 请求上下文与记录 |
| 异常 | 已确认故障、可执行下一步、部分结果 | 详细错误、诊断信息 |
| 已结束 | 结果、实际检查、产物、未完成事项 | 执行与思考记录 |

任务阶段来自真实 plan/task 事件或明确标注的 Agent 陈述。不能以“工具调用 7/10”伪装任务完成率；不知道总量就显示已完成工具数。

## 完成凭据

建议包含实际改动、执行过的检查及结果、产物引用、未完成事项、数据来源。优先从结构化事件生成；如果只得到模型文字，应标明“Agent 报告”，不能展示成桥接器验证结果。

例如进程 exit 0 但测试命令返回失败，必须同时保留这两个事实，不能仅用绿色完成掩盖测试失败。没有收到检查事件时，不得自动写“测试通过”。

## 创新候选及边界

- 恢复卡：展示最后确认状态和恢复选择，复用 OPT-04，不自动重做不明副作用。
- 会话索引：显示项目、Agent、最近活动，复用已有 `/new chat` 和 `/resume`，避免另建不兼容会话体系。
- 简洁/详细模式：变化的是展示，不应改变记录采集完整性和权限。
- 阶段摘要：先用确定性事件汇总；若增加模型摘要，另行核算费用、延迟和误述风险，并保留来源。

## 入口

`src/card/run-renderer.ts`、`src/card/tool-summary.ts`、`src/card/run-state.ts`、`src/agent/types.ts`、`src/bot/channel.ts` 及现有配置/状态卡。

## 验收

- 短任务不会产生不必要的多条状态消息。
- 长任务中用户能区分运行、等待输入、卡片延迟与实际失败。
- 所有“通过”“完成”“已修改”都有可追溯来源；未知就写未知。
- 失败工具、未完成事项不会被成功汇总隐藏。
- 手机窄屏样例检查正文、按钮和重要错误可读；界面文案不暴露无助于用户决策的内部实现名。
- 关闭详细展示后，仍可通过授权的记录入口查阅完整信息。

## 不做

本任务不默认启动多 Agent，不增加公网任务网站，不重写核心运行时，不承诺自动识别任何任务的真实完成程度。

## 实施记录（2026-09-17，基线 5c07de1）

### 已实施：完成凭据分片（最小且可追溯的部分）

- `buildCompletionNotice` / `buildTerminalNotice` 新增 `failedTools`（来自结构化 `tool_result` 事件统计，非模型陈述）：done 且有失败工具时通知显示"✅ 完成 · … · N 个工具失败"，两个事实并存；无失败时文案不变。失败详情仍由工具聚合容器的"失败详情"区承载（既有能力）。
- 现状核对（无需改动的既有合规项）：
  - 进度行"已完成 N 个工具"即规格要求的"不知道总量只显示已完成数"，无伪完成率。
  - "结果在哪里"入口已由 OPT-01/03 覆盖（`/thinking`、`/last full`、`/doctor`）。
  - 运行/失败/中断/超时的区分由终态通知承载（既有）。
  - 短任务消息数、卡片延迟/等待输入区分（后者依赖 OPT-05 纵向闭环，当前所有后端均无等待输入能力，见其矩阵）。

### 未实施：任务视图重设计与自适应信息密度

默认卡片仍是"正文 + 思考面板 + 工具聚合容器 + 终态通知"的结构，没有按短任务/长任务/等待/异常切换信息层级。这一步是对已接受卡片形态的重新设计，涉及用户可见布局的产品取舍，按交接模板应单独分配任务并给出目标样例后再实施。候选设计（分层视图、会话索引、简洁/详细模式、阶段摘要的成本核算）仍以本规格前列内容为准。
